snakemat design seed: how to give Snakemake first-class MATLAB support

## Constraint found while scaffolding (Snakemake 9.17.1, checked 2026-10-09)
- `script:` language dispatch is hardcoded in `snakemake/script/__init__.py::get_language()` by file extension: .py, .ipynb, .R, .Rmd, .jl, .rs, .sh, .xsh, .hy. No `.m`.
- Each language is a `ScriptBase` subclass (PythonScript, RScript, JuliaScript, ...) that writes a preamble injecting the `snakemake` object, then runs the interpreter.
- Official plugin interfaces installed: executor, storage, report, logger, scheduler. None covers script languages. So `script: "foo.m"` cannot be added through a supported plugin API today.

## Prior art to replace
`sutil.matlab` in labpy (pixecog/code/lib/labpy/src/sutil/matlab.py): `matlab2shell(command)` builds `"/storage/share/bin/R2023a/bin/matlab -batch \"restoredefaultpath; ... run(startup.m); <command>\""`. Pain points: hardcoded MATLAB path, repo-root assumption, manual quote escaping, no structured input/output/params, path problems (pixecog brainstate rules were ported to Python partly because bz_ MATLAB code was unrunnable: loadSession removed).

## Design options (not decided)
A. Rule-side helper library (works today): e.g. `shell: snakemat.matlab("myfunc.m")` or a `run:` helper. It serializes the rule's input/output/params/wildcards/threads/resources/log/config to JSON (or .mat) and invokes `matlab -batch` with a generated preamble.
B. Monkeypatch `get_language` to register a `MatlabScript(ScriptBase)` on import, which gives the native `script: "foo.m"` UX. Fragile across Snakemake versions.
C. Upstream PR to snakemake adding MatlabScript (and possibly Octave), with snakemat as the incubator and reference implementation.
D. MATLAB-side `+snakemat` package with a `snakemake` struct/class mirroring R's S4 object. All of A, B and C need this.
Likely path: D + A first (immediately useful in pixecog/labbox), then C upstream, with B as an optional bridge.

## Runtime concerns to cover
- `-batch` (non-zero exit on error) vs `-r`, which exits 0 on error.
- Startup overhead and license checkouts on the cluster.
- `threads` mapped to `maxNumCompThreads`.
- Log redirection to `log:`.
- Configurable MATLAB executable and toolbox paths (labbox, buzcode) via Snakemake config/profile instead of hardcoding.
- `restoredefaultpath` hygiene.
- Data interchange: JSON vs .mat v7.3 for params; MATLAB R2023a on gamma2.

## Open questions
- Distribution name: keep `snakemat`, or follow the plugin catalog convention (snakemake-<type>-plugin-<name>)? That only applies if it becomes a real plugin type.
- Octave support in scope?
- Should MATLAB Compiler Runtime (MCR) executables be a target too, for license-free cluster runs?

## Update 2026-10-09: the report requirement changes the likely path
`snakemake --report` must show the `.m` source the way it shows a `.py` script.
- The report reads code through `script.get_source()` → `get_language()` (`report/__init__.py::RuleRecord.init_source`) and highlights it with `pygments.get_lexer_by_name(language)` (`report/html_reporter/data/rules.py::render_code`). Pygments already ships `matlab` and `octave` lexers, so `get_language()` returning `"matlab"` is all the report needs.
- `shell:` rules only show the command string, so option A alone can never meet the requirement.
- Snakefiles execute in `snakemake.workflow`'s module globals (`_globals = globals()`), and `workflow.py` does `from snakemake.script import script`. Option B therefore has to replace `snakemake.workflow.script` as well as `snakemake.script.get_language`.
- Revised likely path: **D + B first, C upstream** (open the issue once B works), A optional.

## Survey 2026-10-10: existing plugins and demand
- **No existing plugin.** The plugin catalog's types (executor, storage, logger, report, scheduler; a software-deployment interface is in development) include none for script languages. The PyPI names `snakemake-matlab` and `snakemat` are free. snakemake/snakemake has no issues, PRs or Discussions asking for MATLAB, and no Stack Overflow `[snakemake]` question mentions MATLAB. Nothing on Neurostars or MATLAB Answers. (Not searchable: Snakemake Discord, Google Group.) Upstream `main` (PyPI 9.27.0) still hardcodes `get_language()`.
- **Upstream issues that touch MATLAB in passing:** [#308](https://github.com/snakemake/snakemake/issues/308): MATLAB takes every core, so "if you try to run it on a cluster within a single core job, it will promptly get killed". [#2072](https://github.com/snakemake/snakemake/issues/2072): `envmodules: "matlab/R2022b"` not loaded for the second rule.
- **A tutorial says it outright.** Kalenkovich & Levchenko, *A Reproducible MEEG Data Analysis Workflow with conda, Snakemake, and R Markdown* ([tex](https://github.com/kalenkovich/reproducible-MEEG/blob/HEAD/manuscript/reproducible-meeg.tex)): `script:` works for Python, R, Julia and Rust "(Matlab is not supported)". Its workaround `shell: "matlab -r 'clean_and_epoch({input.raw}, {output.epoched})'"` passes the paths unquoted, so MATLAB reads them as variable names; their [issue #27](https://github.com/kalenkovich/reproducible-MEEG/issues/27) files a "quotes within strings" problem under "Tools: Snakemake: Matlab".
- **Workarounds in the wild.** GitHub code search finds ~190 files that mention MATLAB (162 named `Snakefile`, 27 `.smk`; the index covers only part of GitHub). Of 15 sampled, 12 call MATLAB, all by hand:

## Licensing notes 2026-10-09 (not legal advice)
- **The plugin itself:** MIT code that calls the user's own MATLAB and ships no MathWorks code, so publishing it is not a problem. Don't bundle MathWorks files or publish images containing MATLAB. Use "MATLAB" descriptively and add a not-affiliated-with-MathWorks line.
- **Seats:** each job is one MATLAB process and one seat (plus one per toolbox). Recommend `resources: matlab=1` and `--resources matlab=N`.
- **Clusters:** nodes must reach the license server; some license types forbid cluster use (user's responsibility, say so in the docs).
- **Reproducibility:** `conda:` can't provision MATLAB; use `envmodules:`, a configured path, or a container the user licenses. Record the MATLAB version.
- **CI:** `matlab-actions/setup-matlab` gives a sponsored license only for public repos on GitHub-hosted runners. Octave (GPL, called as a separate program) allows license-free tests and helps upstream acceptance.

## Probe 2026-10-12 (R2023a Update 4 on gamma2)
- `run()` refuses `tmpab12.foo.m`, which is the shape of Snakemake's default temp name (`tmpXXXX.<filename>`): "RUN requires a valid MATLAB script". A name starting with a digit (`01_bad.m`) fails as well. MatlabScript must write files under valid identifier names.
- `jsondecode` mangles `my-key` → `my_key` and returns string lists and heterogeneous object lists as cell arrays.
- `matlab -batch "error(...)"` exits 1.
- Cold start plus a trivial script: ~62 s wall.
- `maxNumCompThreads` defaults to 12 on gamma2.
- Octave 10.3.0 (conda-forge, pixi env `octave`): `octave-cli --eval "error(...)"` also exits 1.

## Why upstream never covered MATLAB (2026-10-12)
No maintainer ever decided against it: no issue, PR or discussion proposes it. Only Python, R (3.5.2, Nov 2015) and R Markdown (3.12, 2017) came from the core team. Everything after was contributed by users who needed it: Julia (5.5.0, 2019), Rust (6.7.0, 2021, #1053), Bash (7.14.0, 2022, #1821), Xonsh (8.30.0, 2025, #3310), Hy (9.14.0, 2025, #3824). The last two merged within two weeks and five days.
Likely reasons nobody contributed MATLAB (inferred):
- Snakemake's community is mostly bioinformatics (Python/R).
- Language tests install interpreters through `conda:` (`tests/test_script/envs/{r,julia,bash}.yaml`), and MATLAB can't be installed that way.
- Snakemake's reproducibility story relies on conda and containers.
- `script:` predates MATLAB's `-batch` (R2019a).
- MATLAB is awkward to embed: identifier-only file names, slow startup, license seats.
Consequence: test the upstream contribution against Octave (conda-forge 10.3.0, linux/macOS, not Windows), and keep every MATLAB-side choice Octave-compatible. Octave moved into Phase 0 of the plan.

## Decisions 2026-10-12: strategy and name
- **Strategy: upstream first.** Snakemake has no plugin type for script languages, so the accepted home is Snakemake core, following the five user-contributed languages. Past PR sizes: Hy +159 lines (merged in 5 days), Xonsh +58 (15 days), Bash +349 (5 days), Rust +1,340 (~2 months). The core classes are written as upstream code; this package installs them into today's Snakemake and carries the extras. Post the upstream issue right after the Phase 0 spike, because review queues are long: Perl (#4164, +459, open since April 2026) and marimo notebooks (#4302, +221, open since August 2026) are both waiting. **Template: the merged Bash PR (#1821)**, not the open marimo PR: Bash, like MATLAB, needed its own encoder and preamble (`BashEncoder` + `BashScript`, exact-string encoder unit tests, `rules.rst` section with examples, conda-env integration test). Take today's file layout from the merged Xonsh PR (#3310: `tests/test_script_xsh/`, registered in `tests/tests_using_conda.py`). Avoid copying Hy (#3824): its `tests/test_script_hy/` folder is never run by any upstream test module. The open marimo PR also seems to break `--report`: `notebook.get_cell_sources()` parses Jupyter JSON and raises `NotJSONError` on the PR's own `.marimo.py` test notebook (function-level check; the PR branch was not run end to end).
- **Parked:** a MATLAB software-deployment plugin, once that interface ships in a release. Snakemake `main` depends on it, but 9.27.0 doesn't, and its README calls it "still a work in progress".
- **`snakemake-object`** (PyPI 1.0.0, July 2023, by Johannes Köster): a one-release extraction of the Python, R, Julia and Bash encoders that Snakemake never adopted. Ask in the issue whether a MATLAB encoder belongs in core or there.
- **Name: `snakemake-matlab`** (import `snakemake_matlab`; env vars `SNAKEMAKE_MATLAB_*`). Of the 93 `snakemake*` packages on PyPI, 73 are `snakemake-<type>-plugin-<name>` and 7 are interfaces. That convention covers only the six plugin types. The other 13 use plain descriptive names (`snakemake-wrapper-utils`, `snakemake-testing`, …). We rejected `snakemake-script-plugin-matlab` because it would imply a plugin type that doesn't exist. The repo folder, projio project and GitHub repo keep the name `snakemat` for now.
