snakemat design seed: how to give Snakemake first-class MATLAB support

## Constraint found while scaffolding (Snakemake 9.17.1, checked 2026-10-09)
- `script:` language dispatch is hardcoded in `snakemake/script/__init__.py::get_language()` by file extension: .py, .ipynb, .R, .Rmd, .jl, .rs, .sh, .xsh, .hy. No `.m`.
- Each language is a `ScriptBase` subclass (PythonScript, RScript, JuliaScript, ...) that writes a preamble injecting the `snakemake` object, then runs the interpreter.
- Official plugin interfaces installed: executor, storage, report, logger, scheduler. None covers script languages. So `script: "foo.m"` cannot be added through a supported plugin API today.

## Prior art to replace
`sutil.matlab` in labpy (pixecog/code/lib/labpy/src/sutil/matlab.py): `matlab2shell(command)` builds `"/storage/share/bin/R2023a/bin/matlab -batch \"restoredefaultpath; ... run(startup.m); <command>\""`. Pain points: hardcoded MATLAB path, repo-root assumption, manual quote escaping, no structured input/output/params, path problems (pixecog brainstate rules were ported to Python partly because bz_ MATLAB code was unrunnable: loadSession removed).

## Design options (not decided)
A. Rule-side helper library (works today): e.g. `shell: snakemat.matlab("myfunc.m")` or a `run:` helper. It serializes the rule's input/output/params/wildcards/threads/resources/log/config to JSON (or .mat) and invokes `matlab -batch` with a generated preamble.
B. Monkeypatch `get_language` to register a `MatlabScript(ScriptBase)` on import, which gives the native `script: "foo.m"` UX. Fragile across Snakemake versions.
C. Upstream PR to snakemake adding MatlabScript (and possibly Octave), with snakemat as the incubator and reference implementation.
D. MATLAB-side `+snakemat` package with a `snakemake` struct/class mirroring R's S4 object. All of A, B and C need this.
Likely path: D + A first (immediately useful in pixecog/labbox), then C upstream, with B as an optional bridge.

## Runtime concerns to cover
- `-batch` (non-zero exit on error) vs `-r`, which exits 0 on error.
- Startup overhead and license checkouts on the cluster.
- `threads` mapped to `maxNumCompThreads`.
- Log redirection to `log:`.
- Configurable MATLAB executable and toolbox paths (labbox, buzcode) via Snakemake config/profile instead of hardcoding.
- `restoredefaultpath` hygiene.
- Data interchange: JSON vs .mat v7.3 for params; MATLAB R2023a on gamma2.

## Open questions
- Distribution name: keep `snakemat`, or follow the plugin catalog convention (snakemake-<type>-plugin-<name>)? That only applies if it becomes a real plugin type.
- Octave support in scope?
- Should MATLAB Compiler Runtime (MCR) executables be a target too, for license-free cluster runs?
